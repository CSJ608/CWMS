# ADR-0008 依赖方向守卫与服务接口住在契约包

状态：已接受 ｜ 日期：2026-08-28 ｜ 关联：issue #4、ADR-0003

## 背景

ADR-0003 的依赖方向铁律（功能/策略 → contracts + kernel；内核不 import 策略）
此前靠自觉维护。写守卫脚本的第一天它就抓出了 8 处现行违规：
feat-inbound 直接依赖 core-ledger / core-task / client-registry 的**实现类**，
veto-mixed-lot 直接 import `Ledger` 类。守卫的价值当场自证。

## 决策

1. **守卫进 CI**（`scripts/check-deps.mjs`，零依赖 Node 脚本）：按包的角色
   （kernel / contracts / core-* / plugins / features / apps）检查两张图——
   package.json 的声明依赖与 src 下全部 import 语句；相对导入越出包根同样
   违规。apps 豁免（组合根组装系统是它的职责）；tests 豁免（测试组合真实
   提供者是正当行为）。
2. **服务接口住在 contracts，实现住在各包**（结构化匹配，无需继承）。
   这不是补丁，是 Parnas 信息隐藏的落点：
   - `LedgerReader`（只读视图：find/linesAt/total/snapshot）——策略与校验
     的唯一窗口。**策略看得见账本现状，看不见变更通道**；receive/ship/move
     只出现在 `InventoryLedger` 上，只属于被授权驱动的功能宿主。
   - `TaskServiceView` / `ModuleRegistry<T>` 同理：消费方认识的只是契约。
3. **角色即规则**：允许依赖由包的目录角色决定，不逐包开白名单。
   新角色出现时改守卫 + 提 ADR，而不是私下加例外。

## 后果

- 违规在 CI 三秒内被打回，评审不再靠人眼盯 import。
- 守卫暴露并修复了真实的设计气味：策略层曾能类型化地触碰账本变更 API。
- 合规成本前移：新增跨包引用时，第一反应是"接口该不该进 contracts"，
  而不是"怎么绕守卫"。
