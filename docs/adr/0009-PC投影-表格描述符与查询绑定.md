# ADR-0009 PC 投影：表格描述符与查询绑定

状态：已接受 ｜ 日期：2026-08-28 ｜ 关联：issue #12、ADR-0004/0006

## 背景

ADR-0004 定义了三端投影：PDA 是任务的函数（已落地，PR #9），大屏是指标的函数
（读模型已存在），**PC 是数据的函数**——本 ADR 落地第二端：表格投影（`pc-runtime` 包）。

## 决策

1. **表格描述符是纯数据**（`PcTable`：列定义），功能包登记一次即获得 PC 能力。
   feat-inbound 的改动是十行声明（库存一览的四列），零 UI 代码——与 PDA 命题
   同构复验：端的差异由 runtime 吸收，不由功能包承担。
2. **数据绑定在组合根**：`bindProvider(tableId, provider)` 由组装系统的人调用，
   runtime 只做形状组装（描述符列 + 数据源行）。与 pda-runtime 的 onSubmit
   绑定完全同构——**runtime 纯机制，领域语义住在功能包，连接住在组合根**。
3. **runtime 不校验行内容**：行数据形状对齐列 key 是适配器的责任
   （契约类型彼此对齐时是零成本：StockLine 的字段名即列 key）。
4. **无分页/排序/虚拟滚动**：投影按需付费（ADR-0002），内存账本上这些是
   想象力驱动的复杂度。
5. 同名重绑即替换数据源（热重载友好）；查询每次重新求值——投影跟随领域状态。

## 后果

- 三端中两端已落地且共享同一模式（描述符注册表 + 组合根绑定 + 幂等/查询语义），
  第三端（大屏）只剩"task/changed 事件驱动的读模型"一件事。
- 换 UI 框架 = 换一个消费 `TableView` 的渲染器，功能包与 runtime 均零改动。
- 表格行类型与领域类型的对齐靠命名约定（列 key = 字段名）；出现第二张
  需要转换的表格时，再考虑列映射器，不预先设计。

## 增补（2026-08-29）：filters 描述符字段——列等值筛选

关联：issue #27（agent-lab R3）

**背景**：本 ADR 第 4 条「无分页/排序/虚拟滚动——投影按需付费」。如今 web
渲染器的库存一览需要按库位筛选——过滤字段的第一个真实消费者出现，转正。

**决策**：

1. **`PcTable.filters?: PcFilter[]`**（`PcFilter = { key: string }`）：描述符声明
   本表哪些列可筛。缺省即整表不可筛——筛选面与列定义同为描述符权限，
   功能包不声明，端就无从可筛。
2. **`query(tableId, filter?)`**：filter 是「列 → 期望值」的部分映射，语义为
   **列等值**（行值 === 期望值才命中）。键必须既是表格列、又在 filters 中
   声明；两种越界分开报错（未知列 / 未声明可筛）。空映射等同不筛。
3. **为何是最小语义**：等值是唯一被真实需求要求的操作；范围、模糊、多值、
   排序都还是想象力驱动（ADR-0002 按需付费）。筛选值不做类型转换
   （string/number 原样比较），数值列筛选的转型等第二个需求出现再议。
4. **扩展预留**：PcFilter 取对象形而非裸字符串，后续加操作符
   （如 `op?: 'equals' | 'range'`）是词汇扩展而非破坏性改动；排序走独立
   字段（如 `sorts`），不挤进 filters。
5. **筛选语义住在 pc-runtime**（query 内实现），渲染器只透传参数——
   领域计算不泄漏进端（依赖方向铁律，ADR-0003/0008）。

**后果**：

- feat-inbound 给库存一览声明 `filters: [{ key: 'location' }]`——一行声明，
  与列声明同构；outbound-log 暂无筛选需求，不声明。
- web 的 PC 面板筛选输入只是 query 参数透传（URL 参数 → server.ts →
  `pc.query`），前端零过滤逻辑。
- 非破坏：filters 与 query 第二参皆可选，既有调用与测试零改动仍绿。
