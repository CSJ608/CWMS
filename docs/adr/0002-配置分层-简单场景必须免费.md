# ADR-0002 配置分层：简单场景必须免费

状态：已接受 ｜ 日期：2026-08-28

## 背景（来自真实项目的教训）

既有 WMS 产品是项目制交付：标准产品 + 定制开发 + 配置。实践中发现：
**抽取的通用配置本身设计不合理，导致系统难用——最简单业务场景和最复杂业务场景，
用户感受到的系统复杂度几乎相同。**

这个现象叫**配置的复杂度均摊**：配置面为最难缠的客户单调生长，然后所有客户平摊。
根因有三个：

1. 配置项当了需求垃圾桶——每个定制需求变成一个新开关，而不是被吸收进一个抽象；
2. 开关之间存在隐含组合约束，正确性靠用户脑内模拟布尔矩阵；
3. 没有默认值哲学与分层——简单场景无法"少看"。

## 决策

CWMS 把配置当作与代码 API 同等级的设计对象，立四条规矩：

1. **简单场景免费**：零配置必须跑通最小场景（convention over configuration）。
   默认值是产品决策，不是技术占位。demo 与测试断言了这一点。
2. **复杂度按需付费**：配置分两层——内置缺省（简单仓库）+ overlay 覆盖
   （复杂仓库）。ABC 插件是范本：不配置时是透明直通监听器，配置后才改变行为。
3. **配置项预算制**：新增配置项前必须论证"为什么不能是推断、约定或数据"。
   配置项是永久公共 API——它活在客户的数据里，比代码更难废弃。
4. **配置是数据，策略是脚本，能力是包**：
   - L1 配置（数据：阈值、优先级表、区域划分）→ 实施顾问，目标吃掉 ~70% 变化；
   - L2 沙箱策略脚本（表达式、模板）→ 高级实施，~25%；
   - L3 插件包（本仓库的缝）→ 产品团队做行业版，~5%；
   - L4 第三方插件市场 → **不做**。接缝是公共契约，开放时机不可逆。

## 后果

- 每个策略插件诞生时必须回答：它的缺省行为让简单用户看到了什么？
- 配置组合约束要显式化（schema 校验），不许用户脑内模拟。
- 项目制定制的第一反应是"进 L1 还是 L2"，而不是"加一个开关"。
