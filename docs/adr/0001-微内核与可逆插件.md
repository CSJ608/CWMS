# ADR-0001 微内核与可逆插件

状态：已接受 ｜ 日期：2026-08-28

## 背景

CWMS 的目的之一是实践"一切皆插件"。但这句话如果不加界定，会重蹈 Eclipse 的覆辙：
在理解设计空间之前就把一切承诺成公共扩展点，API 石化、组合爆炸、无人敢动。

核心参照系是 Cordis（Koishi 的微内核，DeepSeek Harness 以 vendor 方式复用）。
它的真正卖点不是"能扩展"，而是**可逆性**：任意加载/卸载插件后，系统行为只与
最终启用的插件集合有关，与中间过程无关。副作用按 LIFO 回滚，加载顺序由
依赖声明（inject）表达而非手工编排。

## 决策

1. **内核语义**：服务以稳定字符串 key 注册（`provide` / `getService`）；插件以
   `inject` 声明依赖，缺失则拒绝挂载；一切注册都是可逆副作用，卸载时 LIFO 回滚；
   提供者卸载时级联卸载依赖者（生命周期包含关系）。
2. **事件只有两种分发模式**：`emit`（观察，不 await）与 `waterfall`（包装，
   短路即决策）。每个事件的模式是公共契约的一部分，集中声明在 contracts 包。
   parallel / serial 待真实需求出现再引入——机制跟着需求走，不跟着想象力走。
3. **内核范围是封闭清单**：可逆机制（kernel）与库存账（core-ledger）属于内核。
   任务状态机（未来 core-task）同样属于内核。**它们不开放实现缝**——
   "可替换的账本"是灾难设计，账务是全系统最不能变的东西。
4. **什么能上缝，过五道闸门**：有多种真实实现吗？接缝比实现稳定吗？
   故障能隔离吗？生命周期可拥有吗？核心需要知道细节吗？
   有一条不过，它就是普通模块，一个文件夹足够。

## 后果

- 每个插件作者必须为每次注册配对 disposer——成本没有消失，转移成了纪律。
- waterfall 的注册顺序 = 包装顺序。由此产生架构约定：**策略（排序）先挂载，
  校验（否决）最后挂载**，校验永远看到最终候选序（demo 第④步是活教材）。
- 组合复杂度 O(N²) 不会消失，靠"事件模式契约 + 短路语义 + 注册顺序约定"驯服。
