# ADR-0006 端 runtime：通用工作流引擎与组合根绑定

状态：已接受 ｜ 日期：2026-08-28 ｜ 关联：issue #2、ADR-0004

## 背景

ADR-0004 决定 PDA 不做"每功能一套页面"，而做一台通用扫码工作流引擎：
功能包只登记 `PdaWorkflow` 描述符。本 ADR 落地该引擎（`pda-runtime` 包），
并回答一个关键问题：**工作流的最后一步采集完数据后，谁来执行领域操作？**

## 决策

1. **runtime 是纯机制**。消费描述符驱动"提示-提交-推进"；校验只有形状级
   （扫码非空、数量正整数）。**领域校验仍属策略缝**——runtime 扫出的库位
   照样要过混放否决（e2e 测试断言了这一点）。端永远不越权替领域做决定。
2. **绑定在组合根**。谁启动会话谁提供 `onSubmit`——PDA 适配器把采集数据
   映射到领域操作（如 `receiveViaTask`）。由此：
   - 功能包零改动获得端能力（本 PR 中 feat-inbound 未改一行）；
   - 依赖方向不被破坏：runtime 只依赖 contracts + kernel，通过 inject
     拿工作流注册表；功能不依赖 runtime。
   真实的 PDA app 将扮演这个组合根角色——它是未来的接缝，不是现在的障碍。
3. **幂等复用 ADR-0005 语义**：opId 全局唯一、重放返回当时快照、
   跨会话复用报错。**最终一步的 opId 原样传给 onSubmit**，实现链式幂等：
   PDA 断网重传 → runtime 重放（不再触达领域）→ 即使领域层也被直接重放，
   任务机 opId 再兜一层底。两层幂等各自独立成立。
4. **onSubmit 抛错时会话原地不动**：先执行领域绑定、成功后才落地状态——
   同 opId 重试从头走，不会留下半推进的会话。
5. **暂不加事件**：v0 用同步返回值；"大屏看作业进度"这类投影需求出现时，
   再以 emit 事件扩展（机制跟着需求走）。

## 后果

- runtime 校验与领域校验的边界有了明确答案：形状归端，领域归缝。
- 描述符 schema 的任何变更（步骤类型、采集键）是契约变更，走 contracts PR。
- v0 会话为内存实现；PDA 真机上的会话恢复由未来持久化缝解决。
