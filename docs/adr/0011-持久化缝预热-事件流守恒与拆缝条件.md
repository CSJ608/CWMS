# ADR-0011 持久化缝预热：事件流守恒与拆缝条件

状态：已接受 ｜ 日期：2026-08-29 ｜ 关联：issue #18、ADR-0001/0003

## 背景

账本目前是内存实现，README 诚实清单写明"持久化是未来的一个 provider 缝"。
交接快照的预热任务是存储接口设计——但缝的准入五问（ADR-0001）第一问
就是"多实现？"：**现在只有一个实现，拆缝即预设计**。预热因此不是建接口，
而是把拆缝的成本与前置条件弄清楚。

设计审查发现一个真实缺口：`Ledger.move()` 只发一个 `ledger/changed` 事件
且只带目标库位——**事件流不守恒**。收/发/移的事件序列无法重放重建账本
（移出侧的扣减在事件流里不存在）。这既是审计洞（看事件流无法回答
"STAGING 的货去哪了"），也是事件溯源式持久化的阻断项。

## 决策

1. **不拆缝、不建存储接口**。第二个实现出现时再拆（五问不过就不缝）。
   接口草案只记录在本 ADR，不进代码。
2. **修复事件流守恒**：`LedgerChanged` 增加可选 `from?: string`（仅 move，
   为移出库位；`location` 保持为目标库位）。重放语义固化为：
   `receive: +qty@location`、`ship: -qty@location`、`move: -qty@from +qty@location`。
   以「重放重建账本」测试作为守恒性的可执行证明——事件流从此具备
   作为审计日志与持久化格式的资格。
3. **拆缝条件与候选形状**（未来第二实现出现时二选一，再立 ADR）：
   - **快照 store**：`load(): StockLine[] / save(lines): void`，账本不变量
     裁决仍在 Ledger 内，store 只管状态落盘。实现成本低，丢事件流。
   - **事件溯源**：追加 `ledger/changed` 事件日志，启动时按上述重放语义
     重建。要求事件流守恒（本次已达成）与确定性重放（已满足：事件即状态
     增量，无外部依赖）。
   - 共同前置条件即本次的守恒修复；差异在是否保留事件日志。

## 后果

- `from` 为可选字段，现有订阅者（大屏投影 todayInboundQty 等）零改动。
- 事件流从"通知"升格为"事实记录"——未来审计、对账、事件溯源共用同一格式。
- 拆缝时的改动面已收敛：`Ledger` 的状态全部经由 `#stocks` 的 get/set/delete，
  换存储只需替换这一个成员的来源，公开 API 与事件语义不动。
